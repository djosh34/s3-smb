# Chaos test audit

## Scope and answer

Audited `main` at **`7abde9d4533bf7e6db813e8993295fc4558772d9`**, the merge of [PR #630](https://github.com/djosh34/s3-smb/pull/630), on 2026-10-06. This is a source and history audit, not a new test run. No product code, test, workflow, protected issue or worker branch was changed. Timings described as results below come from the linked historical reports. Configured durations are not measured runtimes.

**The suite tests recovery and correct bytes much more thoroughly than it tests timely progress on a busy SMB connection.** Most daemon chaos workloads finish one file, including FLUSH and CLOSE, before starting the next. A five-minute stall can therefore look like successful retrying. The tests do not require every later request on that connection to receive an interim or final reply before macOS gives up.

There are important exceptions. Server tests send concurrent READ, WRITE and FLUSH requests through a real engine and an S3 proxy. They check interim replies, credits and unrelated work. Engine tests exercise concurrent writers, small RAM budgets, late requests, restart crashes and copies. Calling the entire suite serial or useless would be wrong. The missing combination is **same-connection queued work, slow cleanup or file locks, memory pressure, and a bounded first-response oracle**.

The history does not support blaming an owner decision to drop chaos. The owner explicitly kept chaos in the release gate, rejected a recommendation to drop its separate suite, and later added Mac S3-outage acceptance. The owner did ask for extensive pruning, late Mac acceptance and restricted reviews. Agents selected the small serial workloads and generous waits. I found no explicit decision to exclude slow CLOSE under S3 outage, to forbid same-client concurrency, or to treat eventual success as sufficient proof of macOS liveness.

### What the Mac evidence establishes

[The investigation on #620](https://github.com/djosh34/s3-smb/issues/620#issuecomment-6010570350) reports eight Mac outage runs with request timeouts, including five restore failures and three passes for the selected test tree. It attributes the missing bytes to the SMB request loop stalling behind CLOSE or locks held by S3 work, rather than an engine byte-mapping error. It also reports a small Linux server regression that fails on main and a concurrent engine stress test that passes.

Those are the investigation's results, not experiments repeated in this audit. In particular, timed-out writes in a run whose checked tree restored correctly are evidence of a bad protocol outcome, not independent proof here of where every lost byte went. The source-level coverage gap is independently visible in the tests below. The same shape in the old JuiceFS implementation makes the historical risk credible, but this audit does not claim a measured JuiceFS Mac S3-outage failure.

### Shared daemon chaos rules

Sources: [`chaos_test.go:30-205`](https://github.com/djosh34/s3-smb/blob/7abde9d/test/e2e/chaos_test.go#L30-L205), [`fixture_test.go:420-536`](https://github.com/djosh34/s3-smb/blob/7abde9d/test/e2e/fixture_test.go#L420-L536).

- Chaos skips without `S3_SMB_CHAOS_SEED`. Each test uses PCG with the seed and an FNV hash of its name. Data, cut points and schedule choices derive from that stream.
- `writeFiles` sorts file names, then calls `writeFile` serially. That helper does CREATE, WRITE, FLUSH and CLOSE. `verifyFiles` checks SHA-256 of each full file, but ranges over a Go map, so verification order is not fixed by the seed.
- Login initially uses a 20-second context. `chaosShare` replaces the share context with **one ten-minute context created when that share is obtained**. It is not a fresh ten-minute deadline per request, despite that shorthand in some discussion. It still allows one silent request to consume minutes.
- All fixture connections use the same client GUID. One supported Mac can have several connections; one-client admission does not mean one outstanding request.
- Random schedules run on timers in a separate goroutine. A seed reproduces random choices, not exact request/fault interleavings, retries, scheduler timing or the number of files completed by a wall-clock loop. No complete event trace is saved for exact interleaving replay.
- Daemon liveness, process exit and race detection help catch crashes. `checkDaemonLog` checks JSON lines and credential markers, not a general assertion that every JSON error-level message is forbidden. Startup retries can be accepted deliberately.
- The seven chaos tests have no per-family sustained request-rate target, dirty-memory pressure assertion, outstanding-request count, first-response histogram, or required fault-kind hit count. The outage test does have an explicit S3-hit check.

## 6. Fault tools and fuzzing

### Fault tools

- [`internal/s3fault/proxy.go:34-45,142-238`](https://github.com/djosh34/s3-smb/blob/7abde9d/internal/s3fault/proxy.go#L34-L238): method/prefix-selectable HTTP error and S3 error code, response header delay, half-response cut, timed outage. [`HoldNextChunkResponse`](https://github.com/djosh34/s3-smb/blob/7abde9d/internal/s3fault/proxy.go#L260-L330) holds the response **after upstream accepted a chunk PUT**. It is not a delayed-commit simulator. Counters include chunk PUTs and an outage event, not a complete fault-hit ledger.
- [`chaos_test.go:148-205`](https://github.com/djosh34/s3-smb/blob/7abde9d/test/e2e/chaos_test.go#L148-L205): fault choice among 500, 503 SlowDown, 100 ms to three-second header delay, cut or none; all/GET/PUT method selection; schedule step 200 ms to two seconds. Network shaping changes delay below 20 ms, optional rate roughly 256 KiB/s to below 8.25 MiB/s, or one-in-eight stalls. Fault scheduling is random, not required coverage of each kind.
- [`internal/netfault/proxy.go:20-24,67-96,186-224`](https://github.com/djosh34/s3-smb/blob/7abde9d/internal/netfault/proxy.go#L20-L224): cuts/refuses connections, restores, delays and rate-limits both directions in at-most-16-KiB pieces, and stalls. It models a TCP byte stream, not packet loss, duplication or reordering independently.
- Proxy tests at [`s3fault/proxy_test.go:77-192`](https://github.com/djosh34/s3-smb/blob/7abde9d/internal/s3fault/proxy_test.go#L77-L192) and [`netfault/proxy_test.go:102-148`](https://github.com/djosh34/s3-smb/blob/7abde9d/internal/netfault/proxy_test.go#L102-L148) check status, outage, hold/release, codes, truncation, drop/restore and shaping against small peers. They validate tools, not Time Machine survival.
- No current general fault for disk full, fsync failure, torn SQLite pages, production host suspension, DNS/TLS stalls or arbitrary late remote commit through MinIO. Some of those classes have narrower storage simulations. The current HTTP fault API has no separately configured slow-body pacing or mid-request-upload cut; do not infer these from the older #271 wish list.

## 7. Mac coverage on main

Sources: [`harness_test.go:111-127,324-354`](https://github.com/djosh34/s3-smb/blob/7abde9d/test/macos/harness_test.go#L111-L354), [`scenario_test.go:29-252`](https://github.com/djosh34/s3-smb/blob/7abde9d/test/macos/scenario_test.go#L29-L252), [`network_test.go:20-151`](https://github.com/djosh34/s3-smb/blob/7abde9d/test/macos/network_test.go#L20-L151), [`backup_test.go:73-118,399-419`](https://github.com/djosh34/s3-smb/blob/7abde9d/test/macos/backup_test.go#L73-L419).

- Baseline contains a small varied tree, including a 4,000,000-byte random file. Kill scenarios add a 1 GiB random file and modify a small file. Network scenarios add 4 GiB. Native Time Machine supplies its own concurrent requests; there is no harness-defined outstanding-request target or recorded seed for this random data.
- `server-kill-restart`, `launchd-kill-restart`, `server-kill-cold`, `server-kill-cold-midpoint`, `client-abort-cold` and `machine-loss` exercise different process/local-state failures. They observe copying and remote object changes, restore the baseline, and where applicable resume and restore new data. Some resume paths allow one retry; launchd and network-outage require the next backup.
- After #630, the midpoint variant obtains its copy by restarting on the old folder after interruption, then starting cold. It is not a timer-triggered copy captured in the middle of a still-running backup. Cold startup may take 15 minutes to allow the ten-minute stale lock.
- `network-drop` cuts the **Mac-to-SMB** link for five seconds during verified band writes. It checks reconnect logs, completion of the same backup and byte-correct restores. A client refusal is “not tested,” with up to three attempts, not a reconnect success. Three refusals fail the harness, even though the helper returns a “not tested” report.
- `network-outage` cuts that same SMB link for at least 45 seconds and waits up to 20 minutes for the backup to end on its own. It reads backupd failure evidence rather than trusting `tmutil` exit status, then checks intact baseline and a successful next backup.
- Harness stage budgets are discover 15, backup 130, recover 85 and scenario 140 minutes; backup completion loop allows 90 minutes; restore command allows 30 minutes. The shell's Go-test timeouts add ten minutes to these stage budgets; workflow job limits are larger again. These are completion budgets, not SMB first-response checks.
- **No main scenario cuts S3 during a native backup.** `s3-outage`, thinning, multiple incrementals, larger rewrite workload and B2 Mac acceptance were task #620 additions, not evidence furnished by these eight existing interruption scenarios.
- Restores verify the selected tree, not every block of the backup image. Kernel request-timeout failure criteria are therefore a useful additional oracle, not redundant with file hashes. Native Time Machine backup encryption, distinct from SMB transport encryption, was explicitly left untested in [#563](https://github.com/djosh34/s3-smb/issues/563).

## 11. What a stronger gate should establish

These are conclusions from the audit, not changes made here. [The newer Linux plan on #620](https://github.com/djosh34/s3-smb/issues/620#issuecomment-6010801110) contains the implementation proposal.

1. Keep byte and recovery checks, but add a separate **first-response oracle** for every request: prompt interim or final, even when earlier storage work cannot finish. A long successful final reply must not erase a missed client deadline.
2. Exercise several files and handles with multiple outstanding requests on one supported client's connection. Include ordinary CLOSE, later-compound CLOSE, delete-on-close, lease ACK and session/tree cleanup while real S3 work or a file lock is held.
3. Prove pressure and fault exposure with counters: dirty budget actually reached, early upload actually started, required fault intercepted, enough requests outstanding, nonempty acknowledged/flushed data checked. Increasing total serial bytes is not enough.
4. Use small deterministic boundary tests for fast diagnosis, then production chunk/budget cases and several seeds. Keep short PR and long gate variants, but vary contention and workload shape as well as duration.
5. Distinguish acknowledged writes, completed flushes and captured copies in the model. Verify after recovery and restart. Include failed operations' possible partial effects without accepting arbitrary bytes.
6. Require negative controls for known gaps and critical oracles. A planted local regression or historical failing revision should demonstrate that the new test rejects silent stalls, false successful writes and missing fault exposure.
7. Make CI report what ran: seeds, completed rounds, fault-hit counts, request progress, memory/resource bounds and skipped cases. “Gate green” should not conceal a short-mode job, an absent measurement producer or a Mac “not tested” result.
8. Retain native Mac S3-outage acceptance as final interoperability proof. Its SMB network-outage cousin exercises a different path. Check both selected-file restores and kernel request-timeout/error evidence.

**Bottom line:** main has substantial fault and durability coverage, but its green chaos gate was not evidence that a busy Mac connection stays responsive throughout an S3 outage. The strongest missing oracle was timely response to queued work, not simply a longer outage or a larger test count.
